# 未完成任务统一状态标定与无缝直接续跑规划 (Subplan v2.5)

本文档依照团队规范维护，定义 CALF 批量实验图形控制面板彻底废除复杂的失败状态与弹窗确认逻辑，实现**“未跑完的一律标为未完成，中断后继续运行直接跑未完成任务”**的技术方案。

---

## 一、需求背景与目标

1. **用户核心指令**：
   - 用户明确要求：“不要这样，没有跑完的直接标记为未完成，中断完继续就直接跑这个未完成的”。
2. **现状缺陷剖析**：
   - 此前运行引擎在任务因用户点击停止、进程中断或退出时，会将任务错误地标记为 `FAILED`（失败）；
   - 面板的 `get_pending_tasks()` 仅查询 `PENDING` 任务，导致点击“启动 / 断点续跑”时无法直接自动拉起刚刚被中断的 `FAILED` 任务，产生“跳过”或需要用户手动多次点击重置的繁琐现象；
   - 界面状态显示英文（`COMPLETED` / `PENDING` / `FAILED`），状态重置时还弹出了多选项对话框，交互冗杂且不符合用户直觉。
3. **目标要求**：
   - **状态彻底简化归一**：全系统任务状态收敛为两态——**已完成 (`COMPLETED`)** 与 **未完成 (`PENDING`)**（运行中的为过渡态 `RUNNING`）；
   - **中断/未完成统标**：任何未彻底跑完测试并输出指标的任务，无论是因为手动停止、关机、异常退出，一律自动直接标定为 **`未完成`**；
   - **直接无缝续跑**：用户点击“▶ 启动 / 断点续跑”时，系统无需任何前置弹窗确认或手动重置，直接自动抓取第一个“未完成”任务继续执行；
   - **界面显示本地化纯粹化**：任务列表中清晰呈现直观的【已完成】、【未完成】与【运行中】。

---

## 二、架构改动与实施方案

### 1. 状态生命周期精简归一 (`state_manager.py`)
- 新增 `mark_pending(task_id, error_msg=None)`：在任务中断、停止或报错时，直接标定状态为 `PENDING`（未完成），不留死锁状态；
- `init_or_resume` 归一化：所有未达成 `COMPLETED` 条件的历史记录，统一自动纠正为 `PENDING`；
- `get_pending_tasks()` 逻辑放宽：直接返回所有 `status != "COMPLETED"` 的任务，按索引排序，确保中断任务永不丢失、立刻排在执行首位。

### 2. 运行引擎中断处理直通 (`runner_engine.py`)
- 在子进程退出时，若 `return_code != 0`、发生 `KeyboardInterrupt` 或捕获异常，一律直接调用 `state_mgr.mark_pending(task_id)`；
- 杜绝将任务落盘为 `FAILED` 阻止下一次启动。

### 3. GUI 控制面板极简直连 (`gui_panel.py`)
- **表格列直观显示**：
  - `COMPLETED` $\rightarrow$ **`已完成`**（绿色高亮）；
  - `PENDING` $\rightarrow$ **`未完成`**（常态深灰色）；
  - `RUNNING` $\rightarrow$ **`运行中`**（蓝色加粗）；
- **进度栏与提示文案收敛**：
  - 显示格式：`进度: X / Y (Z%) | 未完成: N`；
  - 停止后状态栏提示：`批次已暂停。当前任务已标为【未完成】，再次点击【启动 / 断点续跑】将直接继续。`
- **移除冗杂弹窗**：
  - 彻底移除 `_on_reset_selected_task` 中的三项分支确认弹窗，点击即一键设为“未完成”。

---

## 三、实施里程碑 (Milestones)

1. **Phase 1**：修改 `state_manager.py`，实现状态统一归一化为 `PENDING`（未完成），确保 `get_pending_tasks` 覆盖所有未完成任务。
2. **Phase 2**：修改 `runner_engine.py`，中断与非零退出一律标记为 `PENDING`。
3. **Phase 3**：修改 `gui_panel.py`，展示纯粹中文状态【已完成 / 未完成 / 运行中】，移除冗杂弹窗。
4. **Phase 4**：自动化测试验证（模拟运行中断、点击停止、重新启动，确认直接继续运行中断任务）。
5. **Phase 5**：归档 `execution_results.md` 并更新 `public/plan.md`。
